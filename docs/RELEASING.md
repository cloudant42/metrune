# Release procedure

Metrune is a production beta. A release keeps binaries, images, migrations,
documentation, and the supported Compose topology on one reviewed tag.

## Prepare

1. Update crate versions and `CHANGELOG.md`.
2. Run `make check`, `git diff --check`, and the restore drill.
3. Review migration ordering and rollback limits.
4. Verify invitation and reset delivery against the production SMTP provider.
5. Exercise install, enrollment, upload, and analytics on a clean Linux host.
6. Create and push an annotated `vX.Y.Z` tag from the reviewed commit.

## Client artifacts

The client workflow builds and runs `--version` and `--help` on Linux x86_64,
Windows x86_64, Intel macOS, and Apple Silicon. It publishes checksums, a
support-tier manifest, build-provenance attestations, and `client-manifest.json`
— the machine-readable manifest `metrune update` and every mirroring server read.

That manifest is generated by the released Linux binary itself, so its format
cannot drift from the client that parses it, and it is signed with
`METRUNE_RELEASE_SIGNING_KEY`. Set the `MINIMUM_CLIENT_VERSION` repository
variable to move the fleet's version floor. Distribution, mirroring, and key
rotation are described in [CLIENT_DISTRIBUTION.md](CLIENT_DISTRIBUTION.md).

Linux x86_64 is supported in the beta. Windows and macOS artifacts are
experimental until platform-specific enrollment, credential-store, and
watch-mode tests are release gates.

## Server images

The server workflow builds the API and web images from the same tagged commit,
generates image SBOMs and provenance, scans for high/critical findings, and
publishes `SERVER_IMAGE_MANIFEST.txt`. No moving `latest` tag is published.

Put its immutable digests in the private production environment:

```dotenv
METRUNE_API_IMAGE=ghcr.io/<owner>/<repo>-api@sha256:<digest>
METRUNE_WEB_IMAGE=ghcr.io/<owner>/<repo>-web@sha256:<digest>
```

Verify an attestation from a clean machine:

```bash
gh attestation verify \
  oci://ghcr.io/<owner>/<repo>-api@sha256:<digest> \
  --repo <owner>/<repo>
```

Back up PostgreSQL, ClickHouse, and the vault key before rollout. Start the new
API first, verify `/v1/readyz`, then recreate the web service. Keep previous
images and backups until the rollback window closes.

## Release gate

- `make check` and `git diff --check` pass.
- `scripts/restore-drill.sh` passes from a clean project.
- Both images pass the configured vulnerability scan.
- Changelog, support matrix, migration notes, and image digests agree.
- SMTP delivery and a clean-host Linux client flow have been exercised.
- `client-manifest.json` is attached to the release, is signed, and
  `metrune update --check` against a staging server reports the new version.
